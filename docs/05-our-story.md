# 我们的故事

[← 返回目录](../README.md) | [上一章](04-advanced.md)

> 这套系统不是规划出来的，是被逼出来的。
> 以下是真实的时间线，每一条原则背后都有一个具体的踩坑经历。

---

## 背景

2026 年 4 月，一个非技术背景的用户（老X）和他的 AI 助手进入了高强度协作期。

他不是程序员，但他的日常工作涉及多个长期项目——自传体小说写作、自动化工作流管理、技术社群运营、法律法规追踪。每一件事都是持续性的，都需要 AI 记住大量背景信息。

他的 AI 助手（小马丁）有一套持久记忆系统：两个文件——MEMORY.md（5000 字符上限）和 USER.md（2000 字符上限），每轮对话自动注入。另外还有技能库（Skill）和会话搜索（Session Search）。

听起来不错，对吧？

---

## 阶段一：往里塞（记忆膨胀期）

最初几周，每次发现什么有用的信息，就往核心记忆里塞。

项目进度、偏好设定、踩坑教训、环境配置、API 地址、文件路径……什么都往里放。

```
记忆占用率变化：
第1周：  ██░░░░░░░░░░  19%
第2周：  ████████░░░░  48%
第3周：  ████████████  93%  ← 快爆了
```

93% 的时候，问题来了：

- AI 的回答开始"抓不住重点"——你问项目 A，它把项目 B 的信息也掺进来
- 新信息没地方放了——想记住一个新教训，得先删掉一个旧条目
- 条目之间开始矛盾——两个月前写的"请详细解释"和上周写的"回答简洁"打架

**第一个教训：记忆不是越多越好。过载的记忆比没有记忆更危险。**

---

## 阶段二：第一次整理（发现分层的必要性）

2026 年 4 月 10 日，做了第一次系统性的记忆整理。

灵感来自 [MemGPT](https://github.com/cpacker/MemGPT)（一个学术项目，把 AI 记忆类比成操作系统的虚拟内存）。核心思路：

> 不是所有信息都需要"常驻"在 AI 的脑子里。有些信息可以放在外面，需要的时候再加载。

建立了三层记忆模型：

```
L0 核心记忆 ← 每轮对话都加载（贵，但快）
    类比：CPU 寄存器
    
L1 外挂文件 ← 需要时手动加载（中等成本）
    类比：内存

L2 历史搜索 ← 搜索过往对话记录（最便宜）
    类比：硬盘
```

把自动化工作流的详细配置、小说的逐章评估等"深度工作上下文"从核心记忆搬到了独立文件。核心记忆只留一行指针："自动化工作流详情 → 见 workflow-worklog.md"。

```
效果：93% → 48%，23 条 → 17 条，释放了 ~2250 字符
```

**第二个教训：核心记忆是身份证，不是行李箱。只放每次都要用的东西。**

---

## 阶段三：进度分裂危机

整理完以为万事大吉了。然后撞上了一个更隐蔽的问题。

有一天发现，同一个项目的进度出现在了五个地方：

1. **核心记忆里** — 写着"已完成第三步"
2. **工作日志里** — 写着"第四步进行中"
3. **会话书签里** — 写着"第二步和第三步完成了"
4. **技术文档里** — 写着"全部完成"
5. **技能文件里** — 列着一堆待办

五份进度，每份都不一样。**没有一份是完整准确的。**

更恐怖的是：书签是下午写的，工作日志是上午更新的。中间几小时的进展只在书签里，工作日志完全不知道。AI 拿着上午的进度给建议，还说得头头是道——你根本不知道它在用过期信息。

老X问了一个直击本质的问题：

> "为什么我们要在这么多地方记进度？"

答案很简单：**因为没有人规定过"进度只在一个地方记"。** 每次存信息时"哪里方便就塞哪里"，日积月累就成了五份自相矛盾的副本。

**第三个教训：多份副本 = 多个谎言。只有唯一的那一份是真话。**

从此确立"单一进度源"原则——每个项目的进度只在 worklog 里记录，其他地方一律写"详见工作日志"。

---

## 阶段四：暗号系统（解耦革命）

核心记忆瘦了，进度统一了。但新问题又来了：

老X同时在做五件事（小说/自动化工作流/社群/法律/技术研究），每件事都有自己的外挂记忆文件。AI 怎么知道该加载哪个？

灵感来源意外地浪漫——老X觉得这个机制特别像谍战片里的接头暗号：你说一个词，对方立刻知道你是谁、要什么情报。于是"触发词"有了一个更酷的名字：**暗号**。

最初的做法是在核心记忆里直接写路由规则：

```
# 之前的暗号（塞在核心记忆里）
"蜂群马" → 读 memory/workflow/workflow-worklog.md
"小说马" → 读 memory/novel/novel-worklog.md
"社群马" → 读 memory/community/community-worklog.md
......
```

五个域，每个两行，光暗号表就占了核心记忆的 20%。而且每加一个域就多两行，核心记忆又开始膨胀。

2026 年 4 月 13 日，做了一次"全局解耦"重构——

把暗号表单独成一个文件（trigger-table.md），核心记忆里只留一行指针。同时确立了"三不存"原则：

```
核心记忆三不存：
① 不存外挂文件的具体路径
② 不存某个域的具体偏好/流程
③ USER.md 不存某个域的工作细节

一句话判断法：
如果一条信息只在某个暗号激活时才有用 → 不该在核心记忆里
```

**暗号路由链路变成了：**
```
核心记忆 →（只知道一件事）→ "暗号表在 trigger-table.md"
    ↓
trigger-table.md → 各域 worklog 路径
    ↓
worklog → 各子目录/文件按需加载
```

```
效果：87% → 41%。三层暗号路由，核心记忆一行搞定。
```

**第四个教训：AI 的记忆要像图书馆——按需借阅，不是一次性搬回家。**

---

## 阶段五：联动原则（血的教训）

2026 年 4 月 14 日，做完一轮大规模整理后，对所有会话书签做了瘦身。

在瘦身过程中发现了一个严重问题：**自动化工作流的书签里记录了大量进度信息，但工作日志里完全没有。** 包括五个子任务的具体状态、录屏系统的开发进度、任务调度系统的接口细节、驳回监控的功能说明——这些只存在书签里。

如果书签丢了或者被清理了，这些进度信息就永远消失了。

书签本该是"轻量指针"，结果变成了进度的另一个副本——而且是唯一记录了某些进展的副本。**单一进度源原则被悄悄违反了。**

亡羊补牢：花了大量时间把书签里散落的进度信息回填到工作日志里，然后把书签瘦身到只保留指针。

从此确立"存档联动"原则：

```
存档两步走（顺序不能反）：
第一步：更新工作日志（唯一进度源）
第二步：写轻量书签（只记指针和断点）
```

全域瘦身结果：

```
工作流书签：  6742B → 873B  (-87%)
小说书签：    3365B → 633B  (-81%)
社群书签：    1693B → 489B  (-71%)
法律书签：    1478B → 599B  (-59%)
记忆整理书签：2127B → 810B  (-62%)
冗余书签：    1323B → 已删除（内容是另一个书签的子集）

总计：19,983B → 4,239B，瘦身 79%
```

**第五个教训：书签是路牌，不是地图。它告诉你往哪看，不是把所有东西重抄一遍。**

## 阶段六：自动化（零 token 管家）

手工管理记忆太累了。于是建了一套自动化机制：

| 机制 | 做什么 | 什么时候跑 |
|------|--------|-----------|
| 记忆路由器 | 核心记忆里带域标签的条目自动搬到对应外挂 | 每轮对话结束 |
| 利用率追踪 | 统计每条记忆被引用的频率 | 每轮对话结束 |
| 日记归档 | 旧日记自动压缩 | 每轮对话结束 |
| 上下文看门狗 | 上下文占用超标时三级预警 | 每轮对话结束 |

关键设计：**所有自动化都是零 token 消耗**——用后台脚本在对话结束后运行，不占用 AI 的注意力和对话配额。

---

## 一个非技术用户的架构直觉

在这整个过程中，最让人意外的是：**推动架构进化的不是 AI，是用户。**

老X不懂代码，但他说出了最精准的架构判断：

当 AI 把社群的作业放在了主记忆里——
> "理论上来说，社群作业不应该在社群的外挂记忆里么？这样才是最佳的解耦。"

当 AI 只对一个项目做了局部优化——
> "我想知道这是不是全局都适用的？"

当 AI 报告说整理完了——
> "你查了什么文件得出这个结论？给我看原文。"

他用的是日常语言，但说的是软件工程里"关注点分离""全局一致性""证据链"这些核心概念。

> 好的架构直觉不需要技术背景。它来自"东西要放在该放的地方"这个最朴素的道理。


## 最后想说的

这套方法论没有什么高深的理论。五条原则，说白了就是：

1. 进度只写一处
2. 常驻记忆要精简
3. 不相关的不要混
4. 存档前先更新源
5. 定期清理别偷懒

每一条都是被一个具体的、让人抓狂的问题逼出来的。

如果你也在大量使用 AI，如果你也受够了"每次都要重新解释背景"和"进度不知道以哪份为准"——试试这套方法。

不一定要照搬。但至少记住：

> **每件事的进度，只在一个地方记录。**

光这一条，就能解决你 50% 的记忆管理问题。
