## 进阶一：域外挂记忆

### 什么是域外挂

当你同时做的事情越来越多，每个领域的背景信息也越来越丰富。工作日志记进度，但有些信息不是"进度"——比如写作风格指南、项目的技术规范、某个领域的参考资料。

这些信息需要一个地方放，但不能放核心记忆（太大），也不适合放工作日志（不是进度）。

**解决方案：给每个域建一个外挂记忆文件夹。**

```
📁 ai-memory/
├── memory-core.md            ← 核心记忆（常驻）
├── trigger-table.md          ← 路由表（常驻）
│
├── 📁 writing/               ← 写作域
│   ├── worklog.md            ← 进度（唯一源）
│   ├── style-guide.md        ← 写作风格指南
│   └── characters.md         ← 角色设定
│
├── 📁 project-a/             ← 项目A域
│   ├── worklog.md            ← 进度（唯一源）
│   ├── tech-spec.md          ← 技术规范
│   └── meeting-notes.md      ← 会议记录
│
└── 📁 bookmarks/             ← 所有会话书签
    ├── writing-bookmark.md
    └── project-a-bookmark.md
```

### 域内分工

```
worklog.md     → 记"做了什么、做到哪了"（进度）
其他文件       → 记"需要知道什么"（知识）

进度会变，知识相对稳定。分开放，互不干扰。
```

### 加载策略

暗号激活某个域时，加载顺序：

```
1. 先读 worklog.md（知道做到哪了）
2. 按需读其他文件（需要某个知识时再加载）
```

不要一次性把整个域文件夹全塞给 AI。按需加载，省容量省注意力。

## 进阶一：独立暗号路由表（谍战片既视感）

为什么叫"暗号"？因为它的工作方式真的跟谍战片里的接头暗号一模一样——你说一个词，AI 就知道你要干什么、该调出哪套记忆。不用的记忆锁在保险柜里，不会干扰当前任务。

### 基础版 vs 进阶版

基础版里，我们把暗号写在核心记忆里面。但随着域越来越多，这些暗号本身就占了不少空间。

```
# 基础版（写在核心记忆里）
聊写作 → 加载 writing/worklog.md
聊项目 → 加载 project-a/worklog.md
```

进阶版把路由表单独成一个文件，核心记忆里只放一个指针：

```
# 核心记忆里只写这一行
路由规则 → 详见 trigger-table.md
```

```
# trigger-table.md
| 暗号 | 域 | 首先加载 | 备注 |
|--------|-----|---------|------|
| 写作/小说/章节 | writing/ | worklog.md | 写小说时激活 |
| 项目/开发/代码 | project-a/ | worklog.md | 项目A相关 |
| 社群/运营/作业 | community/ | worklog.md | 社群管理 |
| 法律/日报/监管 | legal/ | worklog.md | 法律信息追踪 |
```

### 为什么单独成文件

- 核心记忆更精简（省空间）
- 路由表可以越来越复杂而不影响核心记忆
- 修改路由不用动核心记忆

### 冲突处理

如果一句话触发了多个域怎么办？

```
用户："帮我把项目A的技术方案写成文档"

→ "项目" 触发了 project-a/
→ "写" 可能触发了 writing/

怎么办？以具体名词为准。"项目A"比"写"更具体，加载 project-a/。
```

规则：**越具体的暗号优先级越高。**

## 进阶三：记忆整理（梦整理）

### 什么是梦整理

人在睡觉时，大脑会把白天的经历重新整理——强化重要的记忆，清除无用的碎片。这个过程叫"记忆巩固"（Memory Consolidation）。

AI 的记忆也需要类似的过程。我们借用这个类比，把定期整理 AI 记忆的操作叫"梦整理"——让 AI 也"睡一觉"，醒来后记忆更干净。

### 什么时候该做

```
📅 定期：每周或每两周做一次
⚠️ 触发：核心记忆超过容量的 50%
🔔 信号：发现 AI 回答开始"抓不住重点"
```

### 检查什么

```
一、核心记忆体检
  □ 有没有超过容量上限？
  □ 有没有只在特定域才有用的信息混进来了？
  □ 有没有过时的规则或偏好？
  □ 有没有重复的条目？

二、工作日志体检
  □ 已完成的任务还在"当前活跃"里吗？→ 移到"已完成"
  □ 有没有写了但其实用不到的细节？→ 删
  □ 进度描述还准确吗？→ 更新

三、会话书签体检
  □ 书签有没有变"胖"？（超过 20 行就该瘦身）→ 精简
  □ 书签里有没有重复工作日志的内容？→ 改成指针
  □ 有没有已经过时的书签？→ 删除或归档

四、跨域一致性
  □ 工作日志里提到的进度，和书签里写的一致吗？
  □ 核心记忆里的路由表，和实际的文件结构一致吗？
```

### 整理原则

```
1. 不确定要不要删？先搬到"归档"，别直接删
2. 整理完做一次验证：让 AI 总结它知道什么，看对不对
3. 整理的记录本身也值得保留（"上次清理了什么"）
```

## 进阶四：多层归档

当项目越来越多，有些项目结束了但可能以后还要参考。这时候需要归档层：

```
📁 ai-memory/
├── memory-core.md
├── trigger-table.md
│
├── 📁 active/              ← 活跃项目（暗号路由到这里）
│   ├── writing/
│   └── project-a/
│
└── 📁 archive/             ← 归档（不在路由表里，需要时手动调取）
    ├── project-b/          ← 已结束的项目
    └── old-bookmarks/      ← 历史书签
```

归档的项目从暗号路由表里移除。需要的时候手动告诉 AI "帮我调取 project-b 的归档"。

## 进阶五：记忆分级标签

给核心记忆里的条目加上分类标签，一目了然：

```
🚫 铁律：不可违反的硬规则
⚠️ 注意：容易踩坑的地方
📋 索引：指向外挂文件的指针
🔧 工具：环境和工具相关的信息
✅ 验证：经过确认的正向做法
```

这不是必须的，但当核心记忆里的条目超过 10 条时，标签能帮你快速定位。

## 进阶六：利用率追踪

### 问题

核心记忆里的条目，有些天天被 AI 用到，有些放了几周都没触发过。但你不知道哪些是哪些——它们看起来都一样重要。

如果能知道"这条记忆上次被用到是什么时候"，清理起来就有据可依了。

### 怎么做

给每条核心记忆加一个简单的引用计数或最后使用日期：

```
方法一：手动标注（适合所有工具）

每次整理时，问 AI：
"看看我的核心记忆，哪些你在最近的对话里用到了？哪些没用到？"

没用到的就是候选清理对象。

方法二：自动追踪（适合支持脚本的工具）

在每轮对话结束后，用脚本扫描 AI 的回答：
- 提到了核心记忆里的哪些条目？→ 引用计数 +1
- 连续 N 轮没被提到的条目 → 标记为"冷数据"

冷数据不一定要删，但它们是瘦身时的首选目标。
```

### 分类规则

先把记忆条目分成两大类，处理策略完全不同：

```
行为规则类（铁律、原则、底线）
  → 不管用没用过，永久保留
  → 它们是"交通法规"，不是"参考书"

参考信息类（索引、配置、环境细节）
  → 按引用次数分级：
  → 🔥 热数据（10次以上）— 天天在用，必须留着
  → 🌤️ 温数据（3-9次）   — 经常用，保留或考虑搬到域外挂
  → ❄️ 冷数据（0-2次）   — 基本没用过，候选清理
```

### 真实案例

我们在 34 个对话、79 次命中的数据上跑出了这个结果：

```
🛡️ 11 条规则    → 永久保留（不参与排名）
🔥  2 条核心参考 → 被引用 25-31 次（必留）
🌤️  1 条活跃参考 → 被引用 4 次（保留）
❄️  5 条不活跃   → 0 次引用（候选清理）
```

拿着这份报告做记忆清理，"该删谁"不再靠猜。记忆越多，这个工具越值钱。

利用率追踪的价值不在于精确统计，而在于**让"该不该删"从主观判断变成有数据支撑的决策**。

## 进阶七：自动化体检（记忆管家）

### 问题

前面六个进阶都需要你"记得去做"——记得去体检、记得去看利用率、记得检查联动。但人（和 AI）都会忘。

**如果能用一句话触发全面体检，2 秒出结果呢？**

### 思路

写一个脚本（或让 AI 帮你写），自动扫描所有记忆文件，输出一张"体检面板"：

```
🏠 记忆管家 — 全局状态面板

📊 核心记忆
  MEMORY.md: 42% (2120/5000)
  USER.md:   55% (1107/2000)

📚 会话书签
  项目A书签    650B  🟢
  写作书签     1.4KB 🟡 偏胖

📁 域工作日志
  writing      8.2KB  刚更新
  project-a    3.1KB  3天前更新

🔗 联动检查
  ✅ 全部正常

⚠️ 告警 (1项)
  · 写作书签偏胖(1.4KB)，建议瘦身
```

### 检查什么

一个好的自动体检脚本应该覆盖：

```
1. 核心记忆容量 → 超过阈值就告警
2. 书签大小     → 超过 1KB 标黄，超过 2KB 标红
3. 联动时间差   → 书签比工作日志新太多 = 忘了更新日志
4. 域覆盖度     → 有书签但没对应工作日志 = 可能遗漏
5. 冷数据提示   → 工作日志很久没更新 = 可能需要归档
```

### 告警阈值建议

```
核心记忆   > 60%      → ⚠️ 该瘦身了
用户记忆   > 70%      → ⚠️ 快满了
书签大小   > 1KB      → 🟡 偏胖
书签大小   > 2KB      → 🔴 必须瘦身
联动时差   > 10分钟   → ⚠️ 可能忘了更新日志
日志沉默   > 7天      → 💤 考虑归档
```

> **阈值不是死规则**，根据你的使用习惯调整。比如你每天都在用的域，7 天没更新就是异常；但月度项目 7 天没更新很正常。

### 新增书签怎么办

好消息：**脚本会自动发现新的书签文件**——它扫的是整个书签目录，不需要逐个注册。

唯一需要手动加的是**联动映射**：告诉脚本"这个书签对应哪个域的工作日志"。不加也行，只是联动检查不会覆盖这个书签。

### 触发方式

在暗号路由表里加一行就够了：

```
| 记忆管家/体检 | 跑体检脚本 → 展示面板 → 等用户指令 |
```

以后说"记忆管家"，AI 就跑脚本、出面板、报告警，你决定处理哪个。

### 适用范围

```
✅ 适合：使用 Claude Code、Cursor 等支持脚本执行的工具
🟡 部分适合：ChatGPT（可以用 Code Interpreter 跑脚本，但文件系统受限）
❌ 不适合：纯对话式 AI（无法执行脚本，只能用手动体检清单）
```

不支持脚本的工具，回退到"进阶三：梦整理"的手动清单即可。

## 进阶八：行业对标与演进方向

### 我们不是在孤岛上

2025-2026 年，AI 记忆管理已经成为一个热门领域。几个拿了大额融资的开源项目，和我们在解决同一个问题——只是规模和技术栈不同。了解他们的思路，能帮我们少走弯路。

### 主流项目一览

```
Letta（原 MemGPT）—— 操作系统派
  思路：把 AI 记忆当电脑内存管理
  核心记忆 = 内存（RAM），始终可见
  归档记忆 = 硬盘（Disk），按需调入
  AI 自己决定什么该留在"内存"、什么该存"硬盘"

Mem0 —— 自动提取派（2400万美元融资，41000+ GitHub 星）
  思路：聊天时自动提取关键事实，存成原子化记忆条目
  下次聊天自动检索相关条目注入上下文
  亮点：TTL 自动过期——记忆可以设"保质期"，到期自动清理
  实测：准确度提升 26%，延迟降低 91%，token 节省 90%

Zep / Graphiti —— 时间知识图谱派
  思路：把记忆存成带时间轴的图谱
  每个事实记录"什么时候变为真"和"什么时候被取代"
  适合需要追踪事物变化历史的场景
```

### 我们在版图里的位置

如果把这些项目画在一张图上：

```
复杂度高  │  Letta（自主内存管理）
          │       ↑
          │  Zep（时序图谱）    Mem0（自动提取+向量检索）
          │       ↑
          │  ┌─────────────┐
          │  │ 我们的方法论  │  ← 纯文本，零依赖，人人能用
          │  └─────────────┘
复杂度低  │
          └──────────────────────────────────→
          手动管理                        全自动
```

我们的定位：**低复杂度 + 半自动**。不需要数据库，不需要向量引擎，不需要编程——用 Markdown 文件就能跑。这是我们的优势，也是我们的天花板。

对于大多数个人用户来说，这就够了。但当记忆量增长到一定程度，有些能力确实值得借鉴。

### 三个值得借鉴的方向

#### 方向一：工作日志轮转（借鉴 Letta 的分层思路）

**痛点：** 工作日志只会越来越长。一个活跃了半年的域，日志可能膨胀到 200+ 行、20KB+。每次加载都要读一大坨，AI 的注意力被稀释。

**方案：** 给工作日志加一个"归档层"——做完的事自动沉到归档文件，日志本身只保留当前活跃的内容。

```
📁 writing/
├── worklog.md           ← 只保留当前活跃任务（保持精简）
└── worklog-archive.md   ← 已完成的任务沉到这里

轮转规则：
  · 标记为"已完成"超过 7 天的条目 → 移到 archive
  · archive 文件不设上限，但平时不加载
  · 需要查历史时手动告诉 AI "帮我看一下归档"
```

这就像记账本写满了换一本——旧本子还在柜子里能翻，但你平时只看最新的那本。

**实施难度：** ⭐⭐（中等）——需要调整工作日志的格式规范，加一个轮转脚本或手动规则。

> 📖 详细操作指南见 [工作日志轮转指南](../guides/worklog-rotation.md)

#### 方向二：记忆自动过期（借鉴 Mem0 的 TTL 机制）

**痛点：** 核心记忆里有些条目放了很久没用过，但你不知道哪些该清——删错了怕以后要用，不删又占空间。

**方案：** 给参考信息类条目加一个"保质期"标签。过期不是自动删除，而是在体检时高亮提醒"这条已经过期了，要续期还是清理？"

```
# 核心记忆里这样标注（在条目末尾加标记）：
🔧 公司封了飞书网络，暂时用CLI。(⏰2026-04-22)     ← 到期体检时提醒
⚠️ GitHub从桌面不可达，需外部推送。(⏰2026-04-29)  ← 到期体检时提醒

# 不加 TTL 的条目 = 永不过期（铁律、原则等）
🚫 不得修改任何文件                                  ← 没有⏰，永不过期
```

### 标记格式

```
(⏰YYYY-MM-DD)

  ↑ 半角括号+⏰emoji+ISO日期
  放在条目末尾，简单直观
```

### 哪些该打、哪些不该打

```
❌ 不加 TTL：铁律、行为规则、用户偏好
  → 它们是"交通法规"，不过期

✅ 适合加 TTL：临时环境信息、一次性任务备忘、试验性条目
  → 它们是"便利贴"，过了时效就该撕掉或续期
```

### 体检脚本怎么扫

如果你有自动体检脚本（进阶七），加一个正则扫描就够了：

```python
import re
from datetime import datetime

pattern = re.compile(r'\(⏰(\d{4}-\d{2}-\d{2})\)')
today = datetime.now().date()

for line in memory_lines:
    m = pattern.search(line)
    if m:
        exp = datetime.strptime(m.group(1), "%Y-%m-%d").date()
        days = (exp - today).days
        if days < 0:
            print(f"🔴 已过期{-days}天: {line}")
        elif days <= 3:
            print(f"🟡 {days}天后到期: {line}")
```

### 过期了怎么处理

体检报出过期条目后，你有三个选择：

```
1. 续期 → 把日期改成新的到期日
2. 清理 → 这条信息确实没用了，删掉
3. 转正 → 发现这条会一直有用，去掉 TTL 标记
```

**实施难度：** ⭐（简单）——标注约定 + 体检脚本加一个正则扫描。零依赖，手动加标记就能用。

#### 方向三：跨域经验库（借鉴 Mem0 的 Agent 级记忆）

**痛点：** 有些教训是跨域通用的（比如"大文件要分段读"、"改代码前先备份"），但现在散落在各个域的工作日志里。换个域时，同样的坑可能再踩一次。

**方案：** 建一个公共经验库，存放不属于任何特定域的通用教训。

```
📁 ai-memory/
├── memory-core.md
├── trigger-table.md
├── lessons-learned.md    ← 新增：跨域通用经验库
│
├── 📁 writing/
├── 📁 project-a/
└── 📁 bookmarks/
```

```
# lessons-learned.md 示例
- 大文件（>100行）分段读，不要一次性全塞给 AI
- 改任何文件前，先确认当前内容，再动手
- 遇到异常结果，先怀疑工具/环境问题，不要直接当结论
- 批量操作前先列清单让人确认
```

**实施难度：** ⭐（简单）——建一个文件，把各域里的通用教训搬过去。

### Databricks 的"记忆扩展"理论

2026 年 4 月，Databricks 提出了一个有意思的观点：

> **"Agent 的身份存在于记忆中，而非模型权重中。LLM 只是可替换的推理引擎。"**

什么意思？就是说：换了一个新版本的 AI 模型，只要它读的是同一套记忆文件，它就还是"同一个 AI"。模型是工具，记忆才是灵魂。

这意味着：**你在记忆管理上投入的精力，不会因为 AI 升级而白费。** 模型会换代，但你的记忆架构是跨模型、跨工具、跨时代的。

这也是本项目的核心信念：不绑定任何特定 AI 工具，用最朴素的方式（Markdown 文件）管理记忆，让方法论的生命力超过任何一个产品的生命周期。

### 演进路线建议

```
已落地：
  ✅ TTL 标签约定    → (⏰YYYY-MM-DD) 格式 + 体检脚本自动扫描
  ✅ 工作日志轮转    → 格式规范 + 操作指南（详见 guides/）
  ✅ 跨域经验库      → lessons-learned.md，15 条通用教训

暂时不需要（我们的数据量还没到）：
  ⏳ 向量检索        → 等记忆文件超过 50 个再考虑
  ⏳ 知识图谱        → 等实体关系复杂到纯文本管不住再考虑
```

**原则：能用 Markdown 解决的，就不引入数据库。简单的系统才能长期维护。**
